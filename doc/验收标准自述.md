# AutomotiveGUI 验收标准自述

**提交声明：控件定位路径 C。** 本文是参赛队自行设定的验收目标，不是组委会评分细则，也不把尚未在比赛车机上复测的目标写成已达成结果。赛制依据为[CART Q3 AI 大赛章程 v1.1a](CART%20Q3%20AI%20大赛章程%20v1.1a.md) §4.2、§4.4、§4.5、§4.7、§7 及附录 A。

## 1. 技术路径声明与可核验条件

选择章程 §4.4 的 **C：UIAutomator 控件树 + 视觉兜底**。`perception/capture.py` 同轮采集截图与 XML；`core/graph.py` 的 `router` 在候选足够且目标未被裁剪遗漏时走 tree，模型从候选里选 `node_ref`；XML 不可用、候选不足、目标遗漏或 tree 决策无效时走 VLM，模型依据截图给出位置。VLM 图片坐标由执行层换算成设备坐标。运行时不提供 A/B/C 手动切换。

**路径 C 的通过判据**：至少保留一条真实车机任务中的 tree 决策证据（XML、候选、模型请求不含截图、`node_ref`、ADB 点击），以及一条树不可用时的 VLM 兜底证据（XML 状态、截图请求、视觉定位、实际动作）。两条可以来自不同任务。若现场只证明了树路径或只证明了视觉路径，应按实际能力接受降级评审，不以本文声明代替代码和运行证据。

## 2. 测试前提与统计口径

- **正式环境**：章程指定的 Android Automotive 车机中控主屏；仅使用 CEA1.3 原有应用和指定额外安装的哔哩哔哩、飞书、外卖。安卓手机记录为“链路测试”，不计正式通过率。
- **起点**：每轮记录设备、App 版本、登录态、网络、定位权限和初始页面；复测前恢复同一初始状态。测试者提前确认目标歌曲、店铺、菜品或地址实际存在。
- **成功**：由最终屏幕或可复核状态确认，不仅看模型输出的 `COMPLETE` 或 ADB 命令成功。音乐确认曲名、歌手和播放状态；外卖确认第一家店、招牌菜、购物车数量且未下单；跨应用任务逐项确认消息中的时间、日程与导航目的地。
- **失败/阻塞**：目标存在但操作错误、误报完成或超过限制记失败；应用缺失、服务不可达、测试账号未准备等记环境阻塞，单独报告，不混入成功率分母。不得为提高通过率剔除普通弹窗、页面变化或超时失败。
- **计时与 token**：从提交指令到任务结束的墙钟耗时，含模型、ADB、等待与恢复；token 取模型响应 `usage` 汇总，不使用发送前的 `≈in` 估算值。
- **原始证据**：每轮保存任务原文、最终截图、完整 JSONL、结束汇总及必要的 debug XML/模型请求响应。对外分享前脱敏账号、联系人、消息和密钥。

## 3. 自定量化指标

下表是**提交时承诺的目标值与判定方法**，不是已测成绩。简单/中等/复杂任务定义沿用章程 §4.5；现场新任务与参考任务同类型但实体不同。

| 指标 | 自定目标 | 测量与通过判据 |
|---|---:|---|
| 从零搭建 | ≤10 分钟 | 由未参与开发的人按根目录 README，在干净 Windows 环境安装依赖、连接车机、配置模型并完成一条简单任务；记录总时长和干预次数。与章程 §7.2 的 10 分钟档对齐。 |
| 简单任务准确率 | ≥4/5 | 从同一初始状态连续运行 5 条音乐/视频类任务，至少 4 条在最终界面确认正确内容及播放状态。 |
| 中等任务准确率 | ≥4/5 | 连续运行 5 条外卖类任务，改变关键词或店铺；至少 4 条正确加购且均无未授权下单、支付。 |
| 复杂跨应用任务 | ≥2/3 | 在账号、日程和导航功能均可用的前提下运行 3 条不同时间/地点的跨应用任务；至少 2 条所有子目标均正确。 |
| 简单/中等/复杂任务耗时 | 中位数分别 ≤120/240/300 秒 | 对上述成功和失败的有效运行一并统计墙钟耗时中位数；另公布最大值，不能仅挑最快一次。300 秒是为章程 §9 的现场新任务时段设置的内部目标，现场安排以组委会通知为准。 |
| 中等任务 token 经济性 | 中位数 ≤25,000 token/任务 | 汇总每轮模型返回的输入与输出 token，报告 5 次有效运行的中位数和调用次数；包括首次应用路由和失败重试。 |
| 错误完成率 | 0/10 | 抽取至少 10 次任务结束记录，将 `COMPLETE` 与最终状态逐一对照；缺少证据、店铺/歌曲错误或仅点击过按钮均不得判完成。 |
| 稳定性与有界退出 | 10 次运行中 0 次进程崩溃 | 普通失败须写明原因并结束；默认限制为最多 20 步、480 秒及连续 3 次无进展。区分“任务失败”和“程序崩溃”。 |
| 路径 C 可追溯性 | tree 和 VLM 各 ≥1 条真实车机证据 | 检查 JSONL 的 route、原始 XML、候选、模型请求/响应与实际点击；tree 请求不得附截图。 |
| 实时决策链 | 每次任务均可见 | PC 控制台或运行页面实时显示观察、路由、模型决策、执行、核验、终止；事件按步骤排列并有中文说明。 |

这些阈值是队伍的自测承诺，不代表章程规定了相同的成功率、token 或耗时线。若复杂场景所需的车机日程能力或测试账号缺失，必须记录阻塞与替代验证范围，不能填写“通过”。

## 4. 关键能力的验收方法

| 能力 | 操作 | 应看到的证据 |
|---|---|---|
| 应用直启 | 对当前设备已配置应用下达“打开”及“打开后继续操作”两类指令 | 首次文本路由选择应用 ID，ADB 以当前设备包名启动；包名缓存与设备序列号不符时不使用旧包名。 |
| XML 裁剪 | 使用页面元素多于候选上限的任务 | 目标标签及可点击父行仍在候选中；遗漏目标时可转视觉，不把静态文字当作可点节点盲点。 |
| VLM 降级 | 在 XML 为空、dump 超时或目标不可寻址的页面执行任务 | 有明确 XML 状态和降级日志，视觉坐标换算正确，单步没有无限重决策。 |
| Skill 指导 | 执行匹配与不匹配的任务各一条 | 匹配时载入相应 `guide`，之后由模型依据屏幕出动作；不匹配时不误触，也不把 YAML `steps` 当普通任务自动执行。 |
| Context 管理 | 检查至少一条多步任务的模型请求 | 最近历史、已确认实体和当前观察可核对；tree 轮不附图片；输入 token 与模型返回用量可查。 |
| 核验与恢复 | 制造一次无效点击或普通弹窗 | 有 `verify`、必要的重新观察/恢复日志；连续无进展时停止，不虚报完成。 |
| 安全边界 | 外卖加购、飞书测试消息等任务 | 仅执行指令要求的动作；加购不等于下单，未授权时不得付款或发送额外消息。 |
