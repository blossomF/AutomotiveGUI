# AutomotiveGUI 验收标准自述

本文说明项目交付了什么、如何核验，以及当前仍有哪些限制。当前可从仓库代码确认相关机制已经实现；车机任务成功率、耗时和应用适配效果仍需由实际设备上的测试记录证明。

本文位置：`doc/验收标准自述.md`。文末列出相关文档及其项目路径。

## 1. 技术路径声明

项目采用 **路径 C：优先使用控件树定位，无法可靠定位时使用截图定位**。这是当前实现的技术路径声明，赛事要求仍需以正式章程核对。

- **控件树定位（tree）**：通过 UIAutomator 获取页面 XML，提取可定位的控件。通常有至少 3 个候选时，将候选文本发给模型，由模型选择控件编号 `node_ref`。
- **截图定位（VLM）**：XML 不可用、候选不足、任务目标被裁剪遗漏、tree 决策无效，或需要观察屏幕键盘、自定义滚轮时，改用截图。模型给出图像中的位置，程序换算为设备坐标后执行。
- **应用直启**：当前设备存在已核对的应用缓存时，可先由文本模型选择应用，再通过 ADB 启动。仅要求打开应用的任务可以在直启成功后结束。

对应实现位于 `server/autogui/autogui/perception/capture.py`、`server/autogui/autogui/core/graph.py` 和 `server/autogui/autogui/actions.py`。当前视觉定位直接使用截图像素坐标，不使用网格标号。

## 2. 交付标准自述

### 2.1 已实现的交付内容与核验方式

项目已实现任务执行框架，包括观察屏幕、模型决策、设备操作、结果检查和运行记录。框架具备定位降级、动作参数校验、部分重复行为限制、恢复流程和运行上限；这些机制用于减少错误和无效操作，实际稳定性仍需通过测试核验。

下面列的是**交付内容和验收方法**，不是已经全部验收通过的结论。涉及车机的项目，必须在最终目标设备上执行并留存证据。

| 交付内容 | 当前实现 | 如何核验 | 通过标准 |
|---|---|---|---|
| 环境部署与运行入口 | 提供依赖文件、CLI 和网页面板 | 在新 PowerShell 窗口按部署手册安装，运行离线测试和设备自检 | 离线测试退出码为 0；设备硬检查通过；警告已逐项说明或处理 |
| 自然语言任务执行 | 接收文字指令，通过模型决策和 ADB 操作设备 | 选择目标设备已安装应用，执行一条结果能肉眼确认的任务 | 模型调用与设备操作真实发生；程序报告成功，且屏幕上的结果符合任务要求 |
| 控件树与视觉定位 | 优先 tree，必要时转 VLM；截图坐标换算为设备坐标 | 分别选择控件树可用和需截图定位的页面，对照日志与画面 | 日志能说明定位方式和降级原因；点击位置与目标一致 |
| 任务检查与运行限制 | 参数校验、动作效果检查、部分重复行为限制，以及步数、耗时、无进展上限 | 用可复现的失败任务检查执行结果、恢复和停止原因 | 不执行无效动作参数；受运行限制约束；未完成任务有对应失败记录 |
| 异常恢复 | 对符合条件的动作检查画面变化，必要时反思，并尝试返回、回到桌面或重新启动应用 | 在可恢复的错误页面运行任务，查看 `verify`、`recovery` 和后续画面 | 恢复动作有日志；恢复后重新观察；最终结果与实际画面一致 |
| 应用配置与任务指导 | 应用缓存按设备编号核对，Skill 按应用和任务提供指导 | 在设置页核对包名；执行需多步操作的目标应用任务 | 直启使用当前设备的有效包名；任务指导与当前应用匹配；结果实际达成 |
| 日志与诊断资料 | 控制台进度、JSONL 事件、耗时与模型用量；debug 模式保存诊断文件 | 对照同一任务的控制台、JSONL 与截图/XML | 能找到任务结果、失败阶段和统计；诊断文件与该次任务对应 |

### 2.2 跨应用任务与车机适配情况

框架允许在一次任务中启动或切换应用，并通过多轮观察继续操作，为跨应用复杂指令提供执行基础。不过，**车机应用尚未完成全面适配和验证**，不能仅凭已有框架或 Skill 文件就认定所有应用、所有复杂任务都能成功。

正式验收前需在最终车机上逐项核对：

1. 目标应用的实际包名、版本、登录状态和权限是否满足任务要求。
2. 中控主屏是否选对，目标页面能否提供控件树，截图定位是否准确。
3. 中文输入、滚动、数值滚轮等操作是否在该设备上生效。
4. 跨应用任务中每个子目标是否都达成，而非只打开了第一个应用。
5. 是否留存完整的成功样例和失败样例，能说明未完成的原因。

### 2.3 当前不足及其影响

| 当前不足 | 对使用或验收的影响 | 后续需要补充 |
|---|---|---|
| 完整闭环需要采集、决策、执行与检查等多个环节 | 多步任务可能等待较久；重试、反思和恢复会增加模型调用 | 从实际任务日志分析耗时，不以简化演示推断全部任务性能 |
| 车机应用尚未完整适配 | 包名、页面布局、输入方式或控件树质量变化可能造成任务失败 | 按目标应用和代表任务校准，并补齐车机实测记录 |
| 自绘页面、弹窗和屏幕键盘可能依赖截图定位 | 定位与输入效果受画面、模型能力及页面变化影响 | 核对动作前后画面，留存成功与误定位样例 |
| 自动检查不能覆盖全部任务语义 | 画面变化或模型报告完成，均不能单独证明任务达成 | 验收人员对照指令确认结果，尤其是跨应用任务 |

## 3. 验收证据与记录要求

每条用于验收的任务，应保留以下信息：

| 记录项 | 需要记录的内容 |
|---|---|
| 环境 | 测试日期、代码版本、Python/ADB 版本、模型名称 |
| 设备与应用 | 设备编号、中控屏确认方式、应用名称、包名和版本 |
| 任务条件 | 原始指令、初始页面、登录/权限等前置状态 |
| 实际结果 | 预期结果、屏幕上的最终结果、成功或失败、失败原因 |
| 运行证据 | 对应 JSONL，以及需要时的截图、XML、模型交互诊断文件 |
| 性能 | 本次任务耗时、步数、模型调用次数和返回的 token 用量 |

成功率必须说明测试任务清单、总次数和实际成功次数；性能数字应来自真实运行记录。手机测试只证明相应技术链路，不能代替最终车机验收。分享记录前检查并脱敏。
