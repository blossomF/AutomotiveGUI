## 0. 结论先行

**架构照旧，零件清单要换。** `aidoc/` 的三层设计（LangGraph 大脑 + 薄 MCP 执行 + 自研 ADB 桥）经复核是**成立的**，无需推翻。但有 **7 处"照抄即翻车"** 的具体位置必须先改掉，其中 3 处会直接导致车机上跑不起来（P0）。

一句话方案：

```
LangGraph 状态机（大脑，自研）
   ↓  exec_mode: mcp | local（一个开关，两条路都通）
薄 FastMCP server（13 个工具，工具本体是纯函数）
   ↓
bridge/（抄 android-agent adb.py 的【骨架】，删掉 Portal/stealth/TikTok/pinch，补 3 个车机必需修复）
   ↓ ADB
CEA1.3 车机
```

基座策略维持 `aidoc/参考项目对比分析.md` 的判断：**LightGUIAgent 供闭环骨架、android-agent 供 ADB/MCP 零件、MobileAgent 只供思想不供代码**。这个判断复核后依然正确，但"LightGUIAgent 几乎可以直接用"这个隐含语气要打个折——它的网格自动密度、屏幕探测、卡死检测三处在车机横屏上都不能直接用（§2 表 C 组）。

## 2. 代码级复核：必须改掉的 7 处

### A 组 · 抄 android-agent `adb.py` 时的陷阱（P0，不改则车机上直接坏）

参考文件：`android-agent/gitd/bots/common/adb.py`（965 行，**仅 stdlib 依赖**，见 :9-17 → 可摘取性已确认，这是好消息）

**A-1　Droidrun Portal 快路径必须整个删掉。**
`adb.py:357-420 dump_portal_json()` 靠设备上装的 Portal APK（`content://com.ghostinthedroid.portal`）+ `adb forward` 取无障碍树，比 `uiautomator dump` 快 37 倍（33ms vs 1.2s）。
`aidoc/落地设计文档.md` §3 写着"借鉴 dump_xml（Portal 加速 + uiautomator 兜底）"——**这条要划掉**。章程 §4.2 明确"车机侧仅安装组委会指定的 Bilibili、飞书、外卖，其余保持 CEA1.3 原样"，我们**装不了 Portal APK**。留着它只会每次 dump 都白跑一次 forward + 超时探测，反而更慢。
→ 只保留 `adb.py:456-463` 的 uiautomator 分支，并且改成 `dump /sdcard/x.xml` 后 `exec-out cat` 一次取回（原样可抄）。

**A-2　`type_unicode` 会把车机输入法搞坏。**
`adb.py:262-283`：切到 ADBKeyboard → 广播文本 → 然后**硬编码恢复成 Gboard**（:269 `com.google.android.inputmethod.latin/...`，:282 `ime set gboard`）。
CEA1.3 车机上没有 Gboard。这行执行后输入法被设成一个不存在的 IME，**之后所有输入全废**，且是静默失败（模型只会看到"屏幕没变化"，然后开始转圈）。
→ 移植时必须改成：输入前 `settings get secure default_input_method` 存下原 IME，输入后 set 回那个值。见 `autogui/bridge/input.py`。

**A-3　中文弹窗关闭词表是空的。**
`adb.py:134-150`：`_KNOWN_POPUPS` 全是 TikTok 英文串（"Turn on notifications"…），`_DISMISS_WORDS = {"not now","skip","cancel","dismiss","later","discard"}` 全英文。
车机上飞书/B站的隐私协议是"同意/不同意/以后再说/暂不/关闭"，**一个都匹配不上** → `dismiss_popups()` 在中文环境永远返回 False。
→ 三级结构（指定弹窗→通用词→Back 兜底，`adb.py:690-739`）设计得对，**照抄结构、重写词表**。通用词至少：`以后再说/暂不/取消/关闭/跳过/我知道了/不同意/残忍离开/稍后再说`。
→ 另外 `:726` "跳过宽度 >600px 的节点"这个防误触启发式（防止把视频字幕当按钮点）很实用，**保留**。

**A-4　顺手抄上的两个安全/防呆点，`aidoc` 只提了一个。**
`aidoc` §3 提到了 `normalize_keycode` 白名单（`adb.py:53-68`，防 `KEYCODE_HOME; reboot` 在设备 shell 里执行）——对。
但漏了更要紧的 **`input_text_arg()`（`adb.py:71-82`）**：`adb shell input text` 的参数会**再过一次设备 shell**，而我们输入的是 **LLM 生成的文本**。模型被屏幕上的诱导文案 prompt-inject 出 `$(reboot)` 或 `; rm -rf` 这类串，就直接在车机上执行了。它用 `shlex.quote` 包起来、空格保留 `%s`。**必须抄。**
→ 这条同时是"代码质量/安全"的加分证据：评审读得到，且注释能讲清为什么。

### B 组 · MobileAgent-v2 只抄设计、别抄实现

**B-5　`'A' in reflect` 是个真 bug。**
`MobileAgent/Mobile-Agent-v2/run.py:401` 用子串匹配判断反思结果。反思 prompt 要求模型先输出 `### Thought ###` 再输出 `### Answer ###`，而 `:394` 只 `split("### Answer ###")[-1]` —— thought 部分确实被切掉了，**但**：取 `[-1]` 之后的残余文本里只要含字母 A（英文思考句、"ADB"、"Activity"、任何中文句子里的拉丁字母）就误判成成功。
→ 我们实现成**严格枚举**：取回答首字符，`strip()` 后必须 `in {"A","B","C"}`，否则视为反思失败走保守分支（当作 progress 继续，而不是当成功）。

**B-6　v2 的失败步会从历史里消失，导致我们的无进展检测失效。**
`run.py:401-424`：只有 A 分支 `:402-404` 往 `*_history` 里 append；B（`:419-421` error_flag=True + `back()`）和 C（`:423-424` error_flag=True）都**不记历史**，也**不更新 completed_requirements**（planning 只在 A 分支跑，`:406-415`）。
它的代价：进度摘要在失败后变陈旧；连续踩坑时模型看不见过往尝试。
→ 我们**记录失败步**（标 `failed`），并且用 `aidoc` 提出的**屏幕指纹** `md5(tree 文本 + 降采样像素)` 做无进展检测。指纹法比"同格点击告警"更本质，且 B 分支盲发 `back()` 在车机上危险（可能直接退到桌面、或把对话框关错），我们的恢复梯子是 **Back → Home → 重启 App** 三级，每次只降一级并复验。

**B-7　每步 4 次模型调用要压到 ≤1。**
v2 一步里串了 action + reflect + memory + planning 四次（`:302 / :389 / :151+ / :406`），且 reflect/planning 各带双图。统一 quota 下这是自杀，也直接吃掉 Context 10 分。
→ 定稿成 `aidoc` §4.5 的**分层反思**，并明确阈值：
- **0 次 VLM**：动作是 CLICK/SCROLL 且 `screen_hash` 变了 → 判 progress，直接进下一轮。**（多数步走这条）**
- **1 次 VLM**：`screen_hash` 没变，或该步期望改变却没变 → 发前后双图 + 上一动作，返回 A/B/C。
- memory / planning **不独立调用**：合并进 decide 的同一次输出（decide 一并返回 `action + progress + entities`）。
→ 目标：一次 6 步任务 **VLM 调用 ≤6 次**（对比 v2 的 ~24 次）。这个数字直接写进决策链汇总，就是"Context 10 + 性能 10"的现成证据。

### C 组 · LightGUIAgent 不是"改一个文件就行"

复核：`lightguiagent/` 确有 8 个模块；`agent.py:335-556` 的 `run_task` 闭环骨架、`grid_converter.py`（A–T 列字母，20 列 OK）、`claude_client.py:343-393` 的 JSON 解析校验、`settings.py` 的 pydantic 配置结构 → **骨架方向对，值得抄**。

但下面 4 条要改，`aidoc` 说轻了：

**C-8　抓帧是两次往返，不是 `exec-out`。**
`agent.py:117-135`：`shell screencap -p /sdcard/screenshot.png` → 再 `adb pull`，还落盘、还按时间戳建文件名、末尾 `unlink`。每步多一次完整文件传输。性能 10 分当场丢。
→ 换 android-agent 的 `capture_screencap_png`（`adb.py:48-50`，`exec-out` 直取字节流）**并保留 `strip_to_png_signature`（:36-45）**——后者专门处理"多屏设备 screencap 会在 PNG 前打一行 `[Warning] Multiple displays were found`"。**车机正是多屏设备**，这个裁剪不是可选优化，是必需项。

**C-9　所谓"卡死检测"其实只是 prompt 里的一句话，没有硬保护。**
`aidoc` 说 LightGUIAgent "内置卡死检测（连续同格点击告警、连续相同 explain 告警）"。复核位置在 `claude_client.py:322-338` —— 它做的事是**往 prompt 里追加一段 "⚠️ Warning"**（:329、:337），然后指望模型自觉。程序层面**没有任何限制**：循环只有 `for step in range(1, max_steps+1)`（`agent.py:389`）和 `COMPLETE` 自然结束（`agent.py:491`）。模型决定原地转圈，最多烧掉 20 步 API 额度。
→ 结论：**`guard` 节点是纯自研工作量**，不能算"继承来的"。好消息是 LangGraph 的条件回边正好是表达它的天然载体。

**C-10　动作空间没有 BACK / HOME，恢复靠模型猜"返回键一般在左上角 A1–B3"。**
`config.py:150-156` 的 `ACTION_TYPES` 只有 `CLICK/TYPE/SCROLL/AWAKE/COMPLETE`。`claude_client.py:151-156` 的"导航恢复"指引是让模型**去看左上角网格**。手机竖屏上勉强能凑，车机横屏（状态栏/ dock / 顶部常驻栏布局完全不同）上不成立。
→ 动作空间扩到 **10 个**：`CLICK / TYPE / SCROLL / LONG_PRESS / BACK / HOME / LAUNCH / WAIT / SKILL / COMPLETE / FAIL`。`BACK/HOME` 走 keyevent，`LAUNCH` 走 `am start`（=点图标的程序版，章程允许），`FAIL` 让模型能体面认错而不是硬撑到 max_steps。

**C-11　两处硬编码会在横屏上算错，一处探测在多屏车机上会报错。**
- `settings.py:159-171 _calculate_grid`：目标"~108×120 px/格"，但 `rows = max(15, min(rows, 35))` **把行数下限锁死在 15**（列数上限 20、行数下限 15 —— 纯竖屏假设）。1920×1080 横屏下：`round(1080/120)=9` 被强拉到 **15 行**，格子变成 ~128×72px，又扁又密，模型更难选准。
  → **横屏必须显式写死 `grid: {cols: 20, rows: 10}`**，并把 LightGUIAgent 的 auto 密度算法丢掉（它的 clamp 区间对我们无意义）。
- `settings.py:137-157 _auto_detect_screen`：`subprocess.run(["adb","shell","wm","size"])` **没有 `-s <serial>`**。PC 上同时插手机/模拟器时就探测错设备；且 `wm size` 在多屏车机上未必是中控屏。
  → 我们一律带 serial，并优先用 `dumpsys SurfaceFlinger --display-id` / 实际截图字节解码出的宽高为准（截图尺寸才是 VLM 看到的尺寸，`wm size` 可能不等于它）。
- `config.py:162-165 PRICING`：硬编码 Claude $5/$25 每百万 token（`claude_client.py:401-407` 据此算美元）。GLM 是组委会 quota，**美元数没意义**。
  → 只报 token 数与调用次数，不报钱。
- 另：`config.py:91` 的 `target_size: 1568 # Claude optimal image size` 是 Claude 专属经验值，GLM-VL 未必最优 → 记进 9/19 的 A/B 测试项，别当常量继承。

## 3. 定稿架构

下图聚焦 LangGraph 内部结构；用户文字指令或语音转写经 `main.py`、`Runner.prepare()` 后才进入图中的 `START`。完整入口到结束的流程见[代码流程与联调日志导读](./代码流程与联调日志导读.md)。

```
┌──────────────── 大脑：LangGraph 状态机（core/graph.py，自研） ────────────────┐
│ START→perceive→guard ┬(超限)→finish→END                                       │
│                      └→route ┬(skill 命中)→run_skill→act                      │
│                              ├(树可用)→decide[tree]→act                       │
│                              └(树空/未命中)→decide[vlm]→act                   │
│ act→verify ┬(hash 变)→perceive            ← 0 VLM，多数步                     │
│            ├(done/COMPLETE/FAIL)→finish                                       │
│            └(hash 未变)→reflect[1 VLM] ┬A→perceive                            │
│                                        ├B/C→recovery(Back→Home→重启)→guard    │
└────────────────────────────────┬──────────────────────────────────────────────┘
                                 │ exec_mode: mcp | local
┌────────────────────────────────▼──────────────────────────────────────────────┐
│ 薄 FastMCP server（13 工具，@mcp.tool() 纯套壳；工具本体＝bridge/tools.py 纯函数）│
└────────────────────────────────┬──────────────────────────────────────────────┘
┌────────────────────────────────▼──────────────────────────────────────────────┐
│ bridge/  adb.py(截图/树/输入/错误分级) + input.py(IME 安全的中文降级链)         │
└────────────────────────────────┬──────────────────────────────────────────────┘
                             ADB │  CEA1.3 车机（主屏）
```

**两条不可协商的工程约束：**

1. **工具本体是纯函数。** `bridge/tools.py` 里每个函数不 import mcp、不 import langgraph。MCP 只是给它套一层 schema。因此 `EXEC_MODE` 一个开关就能从 MCP 协议降级到 in-process 直调——**MCP 集成不顺时 10 分钟切走，不阻塞主线**（`aidoc` 这条设计是对的，保留为一等公民）。
2. **MCP 工具一律返回压缩后的 `str`，不返回 dict。** 参照 `android-agent/gitd/mcp_server.py:105-106` 的实际做法（`def list_devices() -> str`）。工具输出会原样进上下文，dict 里那些 `{"ok":true,"code":0,...}` 包装全是白烧的 token。同理：**工具签名里不带 `device` 参数**（android-agent 每个工具都要传 serial，因为它做多设备），我们单设备，启动时绑死，省掉每次调用的一段冗余。

## 5. 关键设计（只写有决策含量的部分）

### 5.1 Context 三层（Context 10 分的正面战场）

| 层 | 内容 | 预算 | 超支时先丢 |
|---|---|---|---|
| 永久 | 任务、声明路径、动作 schema、Skill 清单一句话摘要 | ~600 tok | 不丢 |
| 滑动 | 最近 5 步 `{step, route, action, explain, failed?}` **纯文本** | ~500 tok | 丢最旧 |
| 实体 | `entities` dict（时间/地点/歌名/店名/商品）跨步常驻 | ~150 tok | 不丢 |
| 观测 | tree 模式：候选节点文本列表（**不发图**）／vlm 模式：1 张网格图 | tree ~1–2k / vlm ~1.5k | tree 截断到 top-K |

单次 input 目标 **< 8k**。三条硬规则：
1. **tree 模式永远不发截图。** 这条省掉约 90% 视觉 token，是 Context 分的最大单项来源。
2. **候选节点先过滤再喂**：只留 `clickable="true"` 且（有 text 或有 content-desc 或有 resource-id）的节点，按面积降序取 **top-K（默认 40）**，输出成 `#12 搜索 [960,86]` 这种极紧凑行——`#12` 是 `node_ref`，模型回 `{"action":"CLICK","node_ref":12}`，我们再去查 bounds。**模型永远不复制坐标**，避免它把 `[960,86]` 抄成 `[960.86]`。
3. **反思不带记忆体**：reflect 只给前后两张图 + 一个动作，不回灌历史。

### 5.2 双通道降级＝路径 C 的证据链

声明 C 的**唯一风险**是 AI Reviewer 判定"实际只有 B"（章程 §4.4：虚报按实际给分）。所以降级必须**可被观测**：

- `route` 节点每次都打印 `路径=skill|tree|vlm` 与**判据**（"树 60 节点、命中候选 40" / "树 0 节点" / "tree 模式未拿到合法 node_ref，降级 vlm"）。
- **tree→vlm 的降级是真实代码路径**：`decide[tree]` 返回的 `node_ref` 越界/缺失 → 不报错、不重试，直接改判 vlm 再走一次。
- 交付物里放一次**刻意触发的降级样例**（拿一个自绘/树空的界面跑），日志里留痕。这比任何措辞都有说服力。

判据（9/19 拍板，写进验收自述）：≥3 个 App 树可读 → **C**；1–2 → B；全空 → A。
`aidoc/9-19验收清单.md` 记的 9/14 实测"QQ 音乐 控件树 60 节点"是**利好信号**，C 大概率成立——但该清单同时写着"LightGUIAgent 单循环跑通…模式 B 控件树 60 节点"，而 LightGUIAgent 代码里**根本没有控件树通道**（§2 C 组已复核）。那句里的 60 节点应来自手工 `uiautomator dump`，不是 Agent 输出。**9/19 必须重新用我们自己的 tree.py 在同一台车机上实测一遍再拍板**，不要拿这个数当依据。

### 5.3 Skill 层

YAML 声明式（结构抄 `android-agent` 的 skill.yaml + popup_detectors，**执行器自研**，不引它的 Action/Workflow 类体系）：

```yaml
name: music
app: {package: com.tencent.qqmusiccar}
skills:
  - name: play_song
    params: [song]
    steps:
      - {act: launch}
      - {act: dismiss_popups}
      - {act: click, hint: {text: "搜索"}}
      - {act: type,  arg: song, clear_first: true}
      - {act: wait_for, arg: song, timeout: 8}
      - {act: click, hint: {text: "$song"}}
      - {act: complete}
```

- 每个 `hint` **运行期**经 `bridge.tools.find_node` 解析成坐标（即 tree 定位）。
- **任一步 hint 解析失败 → 整个 skill 抛 `SkillMiss` → route 当场降级到通用通道**。这条"Skill 失败自动兜到 B/A"就是 Skills/MCP 10 分与技术深度 +10 的交汇点。
- `run_skill` 全程 **0 次 VLM**，是性能分的最大杠杆（命中即 ~1s/步）。
- 覆盖 6 个：`music.play_song`、`bilibili.search_video`、`feishu.send_message`、`feishu.create_event`、`waimai.search_and_add`、`navigation.navigate_to`。
- ⚠️ 包名待 9/15 借到车机后 `pm list packages` 实测填，**不要抄 `claude_client.py:160-163` 里的美团/淘宝/微信**（那是手机 App，车机上多半没有）。
