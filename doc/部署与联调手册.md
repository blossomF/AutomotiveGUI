# AutomotiveGUI 部署与联调手册（Windows / PowerShell）

本文按当前仓库代码编写，供新电脑从零部署、手机技术冒烟测试和车机现场联调使用。

适用场景：电脑运行 Agent，通过 ADB 连接车机中控屏。**安卓手机可以验证链路，不能代替车机验收。**

第一次使用时，按第 2～4 节依次操作：准备电脑和设备 → 安装依赖 → 配置模型 → 执行任务。第 1 节是熟悉流程后的检查清单，第 5～7 节用于监测、排错和交付。

本文位置：`doc/部署与联调手册.md`。文末列出相关文档及项目路径。

下文以当前仓库位置 `D:\Workspace\github\automotiveGUI` 为例。你的项目如果放在其他文件夹，只修改 `$repo` 那一行。除明确要求另开窗口外，所有命令都在**同一个 PowerShell 窗口**执行。复制代码框里的内容即可，不要复制代码框外的文字。

## 1. 快速检查清单

| 顺序 | 执行 | 通过标准 |
|---|---|---|
| 1 | Python、ADB 版本检查 | Python ≥ 3.10；`adb version` 正常 |
| 2 | `adb devices -l` | 目标设备的状态列为 `device`，且只有一个目标设备或已固定 `device_serial` |
| 3 | 建虚拟环境、装依赖、`main.py --selftest` | 离线测试退出码 0 |
| 4 | `main.py --check` | 设备硬检查通过，并按第 3 节逐项处理警告 |
| 5 | 配 GLM Key、确认应用包名 | Key 已配置但不回显；目标包确实安装在当前设备 |
| 6 | 执行一条无发送/支付的任务 | 有模型调用和设备操作记录，设备结果符合指令；纯打开任务直启成功时可跳过观察循环 |
| 7 | 核对日志 | 有对应 `.jsonl`；`debug: true` 时有同名诊断目录与 XML/模型交互文件 |

前 4 项只覆盖本地运行和设备通道；**真正的端到端拉通必须包含一次模型调用和一次可观察的设备操作**。没有设备时可做离线测试和语音自检，但无法验证 ADB 主流程。

## 2. 从零准备环境

### 2.1 电脑与设备

这一节只做两件事：**让电脑找到 Python，并让电脑通过 USB 连接设备。** 暂时不用填写模型密钥，也不用准备麦克风。

**第 1 步：准备电脑和设备**

- 电脑使用 Windows，安装 Python 3.10 或更高版本。打开开始菜单，搜索并打开 **PowerShell**，下面的命令都输入到这个窗口。
- 用能传输数据的 USB 线连接安卓手机或车机。在设备设置里打开“开发者选项”和“USB 调试”；不同设备的菜单位置可能不同。
- 保持设备解锁。出现“允许 USB 调试吗？”时，在设备上点“允许”。车机后续操作的目标是**中控主屏**，连接后还要在第 3 节确认截图来自这块屏幕。

**第 2 步：告诉 PowerShell 项目放在哪里**

把下面路径改成你电脑上项目文件夹的实际位置。这个文件夹里应该能找到 `env` 和 `server`。

```powershell
$repo = 'D:\Workspace\github\automotiveGUI'
```

`$repo` 是用来保存项目路径的变量。后面的命令会使用它，因此不要跳过这一行。注意变量名以 `$` 开头，直接复制代码框里的整行即可。

**第 3 步：让当前窗口能运行 ADB，并进入程序目录**

ADB 是电脑控制安卓设备的工具，仓库已自带，无需另行下载。依次执行：

```powershell
$env:Path = (Join-Path $repo 'env\platform-tools') + ';' + $env:Path
Set-Location (Join-Path $repo 'server\autogui')
```

第一行把 ADB 所在文件夹加入当前窗口的命令查找路径（PATH），这样输入 `adb` 就能运行它，程序也能找到它。第二行切换到 `main.py`、`config.yaml` 所在的目录。这两行执行成功时通常没有输出；如果出现红色错误，先检查 `$repo` 是否正确。

这些设置只在当前窗口有效。**关闭窗口后再打开，需要重新执行第 2、3 步。**

**第 4 步：检查 Python 和 ADB 是否可用**

```powershell
py -3 -V
adb version
```

- 第一条应输出类似 `Python 3.12.0`，版本需为 3.10 或更高。
- 第二条应输出包含 `Android Debug Bridge version` 的版本信息。

如果提示找不到 `py`，再执行 `python -V`。如果它能显示符合要求的版本，后续命令里的 `py -3` 都改成 `python`。两个命令都找不到时，需要先安装 Python，再重新打开 PowerShell，从第 2 步继续。

如果提示找不到 `adb`，重新执行第 3 步的第一行。仅用完整路径运行 `adb.exe` 成功还不够：本项目的程序会直接调用 `adb`，所以这里的 `adb version` 也必须成功。

**第 5 步：确认电脑已连接设备**

```powershell
adb devices -l
```

成功输出大致如下（设备编号和型号会与你的设备不同）：

```text
List of devices attached
ABC123456    device product:example model:example device:example
```

看设备编号后面的状态：

| 看到的结果 | 含义 | 你需要做什么 |
|---|---|---|
| 一行设备，状态为 `device` | 电脑已经获得调试权限 | 继续第 2.2 节安装依赖 |
| `unauthorized` | 设备还没允许这台电脑调试 | 查看设备上的授权弹窗，点“允许”，再运行本命令 |
| `offline` | 找到了设备，但连接不正常 | 重新插拔 USB 线，再运行本命令 |
| 只有 `List of devices attached`，下面没有设备 | 电脑没有找到设备 | 检查 USB 调试是否开启、数据线能否传输数据，以及 Windows 是否安装了设备需要的驱动 |
| 有多行设备 | 程序需要知道操作哪一台 | 初次使用可拔掉其他设备；如需保留多台，在 `config.yaml` 中把 `device_serial` 设为目标设备的编号 |

初次连接先用 USB。需要无线连接时，设备还必须已开启对应的无线 ADB 功能；`adb connect <设备IP>:5555` 只适用于设备已在该端口监听的情况，不能代替首次授权。

后面执行文字任务时，电脑还需要能访问配置的 GLM 模型服务，具体配置见第 2.3 节。只有使用语音输入时，才额外需要麦克风和讯飞服务。

### 2.2 Python 依赖

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py --selftest
```

已有 `.venv` 时沿用即可。`requirements.txt` 提供主流程和 pytest；**语音可选依赖不在其中**。若要用 `--voice-test` / `--voice`，再执行：

```powershell
.\.venv\Scripts\python.exe -m pip install -e ".[voice]"
```

`--selftest` 不需要设备、GLM Key 或网络；若安装依赖失败，先处理 Python/包下载问题，不要继续把它诊断成 ADB 故障。

### 2.3 配置 GLM 与语音凭证

完成第 2.2 节后，先在当前 PowerShell 窗口启动面板：

```powershell
Set-Location $repo
.\server\autogui\.venv\Scripts\python.exe .\dist\dashboard_server.py
```

保持窗口打开，浏览器进入 `http://127.0.0.1:8777/settings` 填写模型 URL、名称和 API Key，点击“验证连接”确认可用后保存。面板会把 Key 用 Windows DPAPI 加密写入本机 `config.yaml`；该密文绑定当前 Windows 用户，换机器仍需重新录入。CLI 任务也会读取此配置。配置中有效的 Key 优先于环境变量；需要改用环境变量时，先清空本机配置中的 `glm.api_key`。

需要继续执行第 3 节的命令时，先按 `Ctrl+C` 停止面板，并执行 `Set-Location (Join-Path $repo 'server\autogui')` 回到程序目录；也可另开 PowerShell，重新执行第 2.1 节第 2、3 步。

如果只使用 CLI，请核对 `config.yaml` 的 `glm.model`、`glm.base_url`，并通过当前进程的 `GLM_API_KEY` 环境变量提供 Key。PowerShell 可隐藏输入，再注入当前窗口：

```powershell
$secret = Read-Host 'GLM API Key' -AsSecureString
$env:GLM_API_KEY = [System.Net.NetworkCredential]::new('', $secret).Password
Remove-Variable secret
[bool]$env:GLM_API_KEY
```

最后一行只输出 `True/False`，不打印密钥。使用环境变量时，执行任务的进程须继承设置它的窗口。也可用 `.\.venv\Scripts\python.exe -m autogui.security set glm.api_key` 从 CLI 加密录入。不要把明文密钥或本机配置改动提交到 Git。

语音功能另需 `IFLYTEK_APPID`、`IFLYTEK_API_KEY`、`IFLYTEK_API_SECRET`，也可在面板语音设置区录入，或用 `.\.venv\Scripts\python.exe -m autogui.security set voice.appid` 等命令加密录入对应字段。文字任务不依赖语音凭证。

## 3. 设备和应用配置

在 `server/autogui` 下执行：

```powershell
.\.venv\Scripts\python.exe main.py --packages
.\.venv\Scripts\python.exe main.py --check
```

`--packages` 列出设备上的非系统前缀包名；将要操作的应用包名核对到 `config.yaml` 的 `apps`。已有配置的包名不一定适用于当前设备，必须实际核对。手机冒烟测试时可使用单独的本地 YAML 配置文件，通过 `--config <路径>` 指定；不要把手机包名覆盖进比赛提交的车机配置。

`--check` 会连接设备、抓取截图和控件树，并探测输入方式、检查输入法是否恢复。它会与设备交互，运行前先解锁设备。它不调用模型，也不检查网格设置。

**怎样看懂自检结果**

每一行前面的符号表示检查结果：

- `[✓]`：这一项检查通过。
- `[✗]`：这一项检查失败，先解决问题再运行任务。
- `[!]`：警告。程序可能仍能运行，但需要按下面的说明处理。
- `[i]`：提示，例如没有配置目标应用时会跳过应用包名检查。

以下判据已按当前 `main.py` 的 `cmd_check` 实现核对：

| 输出项 | 实际检查什么 | 怎么处理 |
|---|---|---|
| ADB 连接、型号、Android 版本 | 已绑定设备，并读取设备信息 | 连接时直接报错或程序退出，回到第 2.1 节检查连接和授权 |
| exec-out 抓帧 | 返回的截图能读出宽、高 | 失败时检查连接和设备状态；耗时达到 2500 ms 会提示速度警告 |
| uiautomator dump | 返回的控件树 XML 不为空 | 失败时检查设备状态；耗时达到 3000 ms 会提示速度警告 |
| 可寻址候选 | 统计当前页面可供程序定位的控件数量 | 少于 3 个只报警告，主流程会使用截图定位（VLM）；报告有 3 个或更多也不保证目标一定可定位 |
| 输入策略 | 探测可用的文字输入方式 | 只确认 `ascii` 时，尚未证明能输入中文，需另做实际中文输入测试 |
| IME 未被改坏 | 输入探测前后的默认输入法标识是否相同；IME 就是输入法 | 出现 `[✗]` 时先恢复设备原来的输入法，再重新自检 |
| 自检串行采集耗时 | 本次截图与 XML 采集的耗时合计 | 达到 4500 ms 会提示警告，表示任务响应可能较慢 |
| 应用名称 | 已配置且纳入范围的目标应用，其包名是否在当前设备上安装 | 未安装或包名为空会报警告；在设置页修正包名后保存 |
| 应用直启缓存 | 配置中记录的设备编号是否与当前设备一致 | 不一致时，在设置页重新加载当前设备的应用列表并保存 |

命令结束后，立即执行下面一行查看退出码：

```powershell
$LASTEXITCODE
```

`0` 表示设备硬检查通过，**仍需阅读 `[!]` 警告**；`1` 表示有硬检查失败。如果命令直接报错退出，先按错误信息排查。退出码为 `0` 不代表模型连接、中文输入和最终任务已经验证成功。

车机出现“多屏提示”时，必须另外确认截图确实来自中控主屏，必要时在 `config.yaml` 中设置 `display_id`。自检不会替你判断哪块屏幕是中控。

模型 URL、名称和 API Key 在面板设置页填写，再点击“验证连接”单独检查。当前截图定位直接使用图像上的像素坐标，不再使用网格；图像缩放与质量由 `config.yaml` 的 `image.max_side`、`image.jpeg_quality` 控制。模型连接和图像编码参数都不属于 `--check` 的检查内容。

车机正式联调时，再运行：

```powershell
.\.venv\Scripts\python.exe main.py --dump-report
.\.venv\Scripts\python.exe main.py --mcp-check
```

`--dump-report` 会依次启动 `config.yaml` 中的应用、抓 XML，并写入 `artifacts/dump-report.md`；**仅在包名已校准的车机上运行**。它的“可用”判据是每个 App 至少 5 个候选，而主流程 `tree_usable` 判据是至少 3 个候选；报告用于排查树质量，运行时始终控件树优先、VLM 兜底。`--mcp-check` 验证本地 MCP 会话和工具往返，需要设备；日常运行可保持 `exec_mode: local`。

## 4. 端到端拉通

先选当前设备上确实存在、结果可肉眼确认且无需发送、下单、支付的任务。车机可从已安装的音乐或视频应用选择；手机只做技术冒烟测试。示例中的应用名称应按 `--packages` 与屏幕实际情况替换。

```powershell
.\.venv\Scripts\python.exe main.py "打开 QQ 音乐"
$LASTEXITCODE
```

退出码 `0` 代表程序报告成功，仍要在屏幕和日志里确认任务确实达成；非 0 时查看日志的失败阶段。不要用 `--skill-only` 充当自然语言拉通：它显式执行旧 YAML 配方、跳过模型。普通任务可先使用当前设备已核对的应用缓存，由模型选择应用直启；还需操作或直启未命中时，再观察页面并走 tree/VLM。Skill 提供指导，具体动作仍由模型决定。

如需使用网页面板，在完成依赖安装后，在当前 PowerShell 窗口执行下面两行。第二行启动服务后会持续占用这个窗口，这是正常现象；保持窗口打开，按 `Ctrl+C` 可以停止服务。模型凭证也可以在面板启动后通过设置页录入。

```powershell
Set-Location $repo
.\server\autogui\.venv\Scripts\python.exe .\dist\dashboard_server.py
```

浏览器打开 `http://127.0.0.1:8777/` 下指令，`http://127.0.0.1:8777/logs` 查看回放，`http://127.0.0.1:8777/settings` 设置模型、语音和目标应用。面板默认只监听本机；现场首次拉通建议先用 CLI，便于直接看到错误和退出码。面板调用同一个 `main.py`，读取同一份配置；面板日志页固定读取 `server/autogui/artifacts/logs`。

设置页重启后会从 `config.yaml` 回显模型 URL、名称等参数。API Key 和讯飞凭证的输入框始终留空，页面会分别显示“已保存”“环境变量”“未配置”或“密文无法解密”。DPAPI 密文只能由保存时的 Windows 用户及可用的 DPAPI 环境解开；若提示无法解密，在当前机器的设置页重新输入并保存。不要把其他用户的密文当作可跨机器使用的凭证。设置页只对 GLM API Key 和讯飞 API Secret 加密；讯飞 AppID、API Key 按当前实现明文保存。本机凭证配置不要提交到 Git。

语音通道单独验证，避免把麦克风、ASR、模型和 ADB 故障混在一起：

```powershell
Set-Location (Join-Path $repo 'server\autogui')
.\.venv\Scripts\python.exe main.py --voice-test
# 识别正确后，再试：
.\.venv\Scripts\python.exe main.py --voice
```

## 5. 运行环境监测

以下日志命令以当前 `log_dir: artifacts/logs` 配置为例；路径相对于 `server/autogui`。CLI 修改 `log_dir` 后需同步修改查日志的路径，面板日志页不会自动跟随。

| 时机 | 监测项与命令 | 异常含义 / 处理 |
|---|---|---|
| 启动前 | `adb devices -l` | serial 不是 `device`：先处理 USB/授权；多设备时固定 serial |
| 启动前 | `Test-NetConnection llm.thundersoft.com -Port 443`（按实际 `glm.base_url` 改主机） | 只能证明网络端口可达，不能证明 Key、模型名或额度可用；后者以实际模型调用为准 |
| 启动前 | `[bool]$env:GLM_API_KEY` | `False` 且配置里也没本机密文时，模型无法初始化 |
| 每次任务 | 控制台 `Step`、`route`、`decide`、`act`、`verify`、`finish` | 有决策但无 `act`：查动作校验/重复 Skill；反复 `vlm`：查 XML 候选和截图 |
| 每次任务 | `artifacts/logs/*.jsonl` 最新文件及同名诊断目录 | 没有新日志：检查日志路径、文件写入权限，以及是否已进入任务执行；有 `glm_error`：查网络、凭证、配额和响应 |
| 现场持续 | 设备连接、端口 8777（使用面板时）、日志增长、磁盘可用空间 | 设备掉线/日志不写入/磁盘空间不足会使演示结果不可追溯 |

在另一个 PowerShell 窗口持续查看最新一次任务的决策链：

```powershell
$repo = 'D:\Workspace\github\automotiveGUI'
Set-Location (Join-Path $repo 'server\autogui')
$latest = Get-ChildItem .\artifacts\logs -Filter '*.jsonl' -File |
    Sort-Object LastWriteTime -Descending | Select-Object -First 1
Get-Content -LiteralPath $latest.FullName -Tail 30 -Wait
```

`-Wait` 会持续占用这个查看日志的窗口，按 `Ctrl+C` 停止。这个命令只跟踪选中的文件；启动新任务后需重新执行选取最新日志的命令。若还没有 `.jsonl`，先跑一条任务，再执行上述命令。运行结束后可以筛查关键异常和最终状态：

```powershell
Get-Content -LiteralPath $latest.FullName |
    ConvertFrom-Json |
    Where-Object { $_.phase -in @('error', 'glm_error', 'finish') } |
    Select-Object t, step, phase, msg, success
```

使用面板时，另查本机端口；长时间联调时检查设备连接和日志所在磁盘：

```powershell
Get-NetTCPConnection -LocalPort 8777 -State Listen -ErrorAction SilentlyContinue
adb devices -l
Get-PSDrive -Name D | Select-Object Name, Used, Free
```

`Get-NetTCPConnection` 没有输出只说明面板端口未监听；CLI 模式不需要该端口。换盘符部署时，相应修改 `Get-PSDrive -Name D`。

`config.yaml` 当前 `debug: true`：每次任务会保存截图、每次 XML dump、候选文本、发给 VLM 的截图，以及带 `call_id` 的 GLM 请求/响应。文件位于与 `.jsonl` 同名的目录。它们可能包含账号、聊天内容、任务文本；分享或上传前检查并脱敏。诊断结束后可将 `debug` 改为 `false` 减少磁盘占用，但 `.jsonl` 决策链仍会保留。

## 6. 常见故障定位

| 现象 | 先查 | 下一步 |
|---|---|---|
| `adb` 无法识别 | `adb version`、当前 `$env:Path` | 将仓库 `env\platform-tools` 加入**运行 Agent 的同一进程环境** |
| `adb devices` 只有表头 | USB 线、设备 USB 调试、授权弹窗 | 重插数据线，确认驱动和设备端授权；不要直接调模型 |
| `unauthorized` / `offline` | `adb devices -l` | 在设备上重新授权；必要时重连 USB，再核对 serial |
| 多设备报错 | `config.yaml: device_serial` | 填目标设备在 `adb devices -l` 的 serial |
| `--check` 截图或 XML 失败 | ADB 状态、多屏、设备是否锁屏 | 先确认目标中控屏可见，并查看自检控制台错误；任务诊断文件只在执行任务且开启 debug 后生成 |
| GLM Key 缺失或请求失败 | `[bool]$env:GLM_API_KEY`、配置的 base URL、`glm_error` | 区分网络不可达、鉴权失败、模型名错误和配额不足；不要在日志里粘贴 Key |
| `--check` 提示候选不足 | 当前页面是否能提供可定位的控件 | 少于 3 个候选会改用截图定位；这是定位方式变化，仍需通过实际任务确认效果 |
| 长时间重复动作或无进展结束 | 最新 `.jsonl` 的 `route/decide/verify` | 对照截图、XML、模型响应判断是定位错、页面加载慢还是模型决策错 |
| 面板能打开却跑不了任务 | 面板的 Python 环境、GLM Key、ADB PATH | 停止面板后在原窗口用 CLI 排查；也可另开窗口并重新设置路径。面板子进程继承启动窗口环境 |

## 7. 交付前核对

1. 在**干净的新 PowerShell 窗口**按本手册从头做一次，记录安装和拉通耗时。
2. 用最终车机跑 `--check`、`--dump-report` 和至少一条真实任务；核对中控屏、包名及 tree→VLM 降级日志，保存成功和失败样例。
3. 留下一份可供评委复现的命令记录、车机 serial、Python/ADB 版本、任务 JSONL 与诊断目录；日志对外提供前脱敏。
4. 查看 `git status --short`，确认没有密钥、本机手机配置或诊断文件准备入库。比赛主场景以章程限定的车机和应用为准。

日志中的 `perceive / route / decide / act / verify / finish` 分别表示：获取屏幕信息、选择定位方式、模型决定动作、执行动作、检查动作结果、结束任务。排错时先在第 5 节找到本次日志，再对照第 6 节定位问题。
